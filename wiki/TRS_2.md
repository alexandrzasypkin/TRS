# 2. КОНЦЕПЦИЯ И ФИЛОСОФИЯ

[↑ Вернуться к оглавлению](Home.md)


Здесь описаны фундаментальные концептуальные решения, определяющие архитектуру и функционирование системы.  
Раздел 2 раскрывает философию TRS и объясняет, почему система строится не на блокчейне, а на принципах PKI.

------------------------------------------------------------------------

## 2.1. Основная идея: Value Routing вместо Blockchain

### Value Routing (Маршрутизация ценностей)

**Определение:**  
Механизм передачи активов через подписанные сертификаты без централизованных реестров.

**Описание:**  
Основной принцип TRS — движение активов фиксируется цепочкой сертификатов X.509. Каждая операция обмена представлена как Routing Transaction (маршрутная транзакция) — совокупность связанных операций, включающая отзыв старых и выпуск новых сертификатов, фиксируемая в журнале Routing Core.

В отличие от блокчейна, где каждая транзакция записывается в распределённый реестр и требует консенсуса всех узлов, в TRS передача актива происходит через Asset Transfer (передачу актива) — перемещение права собственности между клиентами, реализуемое через Atomic Swap (атомарный обмен). Исходные сертификаты отзываются, новые выпускаются на имя получателей.

**Ключевые отличия от блокчейна:**

- Нет глобального реестра — каждый клиент хранит только свои сертификаты в PKCS#12 Wallet (кошельке PKCS#12)
- Нет консенсуса — операции подтверждаются CA (Центром сертификации), а не сетью узлов
- Нет майнинга — выпуск сертификатов происходит мгновенно без вычислительных затрат
- Trust Chain (цепочка доверия) вместо blockchain — последовательность сертификатов от клиента до корневого CA позволяет проверить подлинность

- **Затраты:** Blockchain требует значительных ресурсов на Mining/Gas. TRS опирается на стандартную PKI-инфраструктуру с нулевыми вычислительными затратами.

- **Хранение:** Blockchain использует бесконечный Ledger, где каждый блок добавляется навсегда. TRS использует конечную Trust Chain с периодической Novation (новацией) — Settlement сертификат погашает все промежуточные.


- **Novation:** В TRS цепочка сертификатов (Cert \#001 → \#002 → \#003) завершается Settlement сертификатом (#SETTLE), который погашает все предыдущие через Asset Revocation. Система начинает новый цикл с чистого листа.

## 2.2. Почему PKI вместо блокчейна

### Преимущества инфраструктуры открытых ключей (PKI)

**Технологическая зрелость:**  
PKI — проверенная временем технология, используемая в критических системах более 30 лет. Стандарты X.509, PKCS#12, CRL/OCSP широко распространены и встроены в операционные системы (iOS Keychain, Android Keystore, Windows CertStore, macOS Keychain).

**Юридическая значимость:**  
Сертификаты X.509 признаются в большинстве юрисдикций как юридически значимые электронные подписи (eIDAS в ЕС, ФЗ-63 в РФ). Блокчейн-транзакции не имеют однозначного правового статуса.

**Производительность:**  
Online Mode в TRS обеспечивает подтверждение транзакции за 5–20 секунд против минут/часов в блокчейне. CA выпускает сертификаты мгновенно без необходимости достижения консенсуса между узлами.

**Энергоэффективность:**  
TRS не требует вычислительных мощностей для майнинга (PoW) или стейкинга (PoS). Smartphone Node (смартфон как узел) может выполнять функции Routing Core и CA, используя встроенные PKI-средства.

**Простота внедрения:**  
Universal PKI Environment — концепция проектирования TRS, обеспечивающая работу без дополнительного ПО. Система использует только встроенные PKI-механизмы ОС и браузеров. TRS реализована на стандартных PKI-инструментах (OpenSSL, X.509, PKCS#12), которые широко распространены, проверены временем и доступны на 99% устройств.

**Масштабируемость:**  
TRS поддерживает как Stand-alone Mode (автономный режим с одним CA) для корпоративных систем, так и Federation (федерацию) — распределённую модель доверия, где несколько CA подтверждают операции совместно через Federation Quorum (кворум федерации).

## 2.3. Прозрачность без глобального реестра

### Public Repository (Публичный репозиторий)

**Определение:**  
Открытое хранилище сертификатов и CRL (списков отозванных сертификатов).

**Описание:**  
Public Repository публикует активные и отозванные сертификаты, обеспечивает прозрачность и проверку статусов. Реализуется как простая HTTP-директория с \`.crt\` и \`.crl\` файлами, доступ через URI.

**Механизм прозрачности:**

Любой участник может проверить подлинность Asset Certificate (сертификата актива) через:

- CRL (Certificate Revocation List) — список отозванных сертификатов
- OCSP (Online Certificate Status Protocol) — протокол проверки статуса сертификата в реальном времени

Double-Spending Prevention (Предотвращение двойного расходования) — механизм, гарантирующий однократное использование каждого сертификата. При передаче активов исходный сертификат отзывается через Asset Revocation (отзыв актива), его статус публикуется в Public Repository.

**Отличия от блокчейна:**

- Нет необходимости хранить всю историю транзакций — только актуальные сертификаты и списки отзыва
- Нет необходимости синхронизировать терабайты данных — клиент загружает только свои сертификаты
- Проверка выполняется через Trust Chain — последовательность сертификатов от клиента до корневого CA
- Audit Log (журнал аудита) — неизменяемый журнал всех операций ведётся Routing Core для целей аудита и арбитража. Фиксирует выпуск, отзыв, подписи и публикации. Доступ к Audit Log ограничен — используется для расследований и разрешения споров через Arbitrator (арбитра), но не является публичным глобальным реестром

## 2.4. Пользователь как узел доверия

### Client (Клиент) — основная учётная единица

**Определение:**  
Основная учётная единица TRS — физическое лицо, организация или шлюз.

**Описание:**  
Каждый клиент имеет свой сертификат X.509 и участвует в операциях по единым правилам PKI. В TRS не существует привилегированных ролей — все участники равноправны.

**Типы клиентов:**

- User (Пользователь) — физическое лицо, использующее PKCS#12 Wallet для транзакций. Совершает операции онлайн или офлайн через мобильное приложение
- Gateway (Шлюз) — доверенная точка входа/выхода активов. Подтверждает происхождение ценностей через Asset Registration (регистрацию актива)
- Validator (Валидатор) — независимый узел, проверяющий подписи и целостность транзакций. Может входить в Federation Quorum и подтверждать корректность обмена
- Arbitrator (Арбитр) — независимая сторона для разрешения спорных ситуаций. Решение оформляется как подписанный документ

**Равноправие участников:**

Каждый клиент выполняет функции узла доверия:

- Хранит свои активы в PKCS#12 Wallet (хранилище ключей и сертификатов)
- Подписывает транзакции своим ключом, создавая Transaction Record (запись транзакции) — подписанный всеми участниками документ сделки
- Проверяет подлинность чужих сертификатов через Trust Chain
- Может работать в Offline Mode, обмениваясь сертификатами локально (QR/NFC)

Smartphone Node — устройство, выполняющее функции Routing Core и CA, используя встроенные PKI-средства. Любой пользователь может развернуть полноценный узел TRS на своём смартфоне.

**PKCS#12 Wallet — единый контейнер для клиента и активов:**

В TRS клиентский PKCS#12-контейнер может одновременно содержать как Client Certificate (для идентификации клиента), так и один или несколько Asset Certificates (для владения активами). Это обеспечивает единый контекст подписи и хранения без дублирования ключей.

Преимущества единого контейнера:

- Подпись транзакций выполняется одним приватным ключом без пересоздания пары для каждого актива
- Все сертификаты (идентификатор клиента и активы) хранятся в одном файле, удобном для резервного копирования и офлайн-переноса
- При передаче .p12 (или части сертификатов из него) можно подтвердить владение активами без доступа к Routing Core

## 2.5. Офлайн-возможность и автономность

### Offline Mode (Офлайн-режим)

**Определение:**  
Режим транзакции без подключения к интернету.

**Описание:**  
Участники подписывают и обмениваются сертификатами локально (QR/NFC), синхронизация происходит позже через Wallet Synchronization (синхронизацию кошелька) — обновление локальных сертификатов клиента с Public Repository.

**Механизм офлайн-обмена:**

1\. Два клиента встречаются без доступа к сети  
2. Создают Transaction Record — подписанный документ сделки с идентификаторами, активами, суммами и подписями  
3. Обмениваются сертификатами через QR-код или NFC  
4. Каждый сохраняет подписанную транзакцию в своём PKCS#12 Wallet  
5. При подключении к сети происходит Wallet Synchronization с Routing Core  
6. Routing Core проверяет подписи и выпускает новые сертификаты

**Grace Period (Период отсрочки):**

Интервал, в течение которого офлайн-сделка может быть оспорена до синхронизации с Public Repository. Применяется для защиты от мошенничества в офлайн-режиме.

**Преимущества автономности:**

- Работа в зонах без покрытия сети (удалённые регионы, подземные помещения)
- Независимость от сбоев интернета или серверов
- Возможность совершения сделок в любых условиях
- Сохранение конфиденциальности — транзакция не публикуется мгновенно

**Сравнение режимов:**

- Online Mode — режим мгновенной транзакции с проверкой CA и публикацией в реальном времени. Среднее время подтверждения — 5–20 секунд
- Offline Mode — транзакция подтверждается при следующей синхронизации, но гарантирует возможность обмена в любых условиях

## 2.6. Простота развёртывания — работает везде

### Universal PKI Environment (Универсальная PKI-среда)

**Определение:**  
Концепция проектирования TRS, обеспечивающая работу без дополнительного ПО.

**Описание:**  
Система использует только встроенные PKI-механизмы ОС и браузеров. TRS реализована на стандартных PKI-инструментах (OpenSSL, X.509, PKCS#12), которые широко распространены, проверены временем и доступны на 99% устройств. Не требуются специализированные библиотеки, блокчейн-узлы или проприетарное ПО.

**Поддержка платформ:**

- iOS — встроенный Keychain для хранения сертификатов
- Android — встроенный Keystore для криптографических операций
- Windows — встроенный CertStore для управления сертификатами
- macOS — встроенный Keychain для безопасного хранения
- Linux — стандартные утилиты OpenSSL
- Браузеры — нативная поддержка X.509 ClientAuth

**Stand-alone Mode (Автономный режим):**

Конфигурация с одним CA, работающая на любом устройстве без внешних зависимостей и федерации. Минимальные требования:

- CA + Routing Core (на одном устройстве)
- PKCS#12 Wallet для хранения ключей
- Веб-сервер (Nginx, Apache или встроенный FastCGI)

**Smartphone Node (Смартфон как узел):**

Устройство, выполняющее функции Routing Core и CA. Используя встроенные PKI-средства, может выпускать, подписывать и проверять сертификаты. Полноценный узел TRS можно развернуть даже на смартфоне, обеспечив выпуск, маршрутизацию и проверку сертификатов без подключения к внешним сервисам.

**Federation (Федерация) — опциональное расширение:**

Распределённая модель доверия, где несколько CA подтверждают операции совместно. Повышает надёжность и исключает монополию одного центра. Routing Federation (федерация маршрутизации) — сеть доверенных узлов TRS, объединённых общими правилами подписания, поддерживает мультиподписи и совместную валидацию через Federation Quorum (кворум федерации) — минимальное количество подписей CA для подтверждения операции (например, 3 из 5).

**Философия простоты:**

TRS следует принципу минимализма — использовать только то, что уже существует и доказало свою надёжность. Вместо создания новой технологии, TRS объединяет проверенные стандарты в универсальную инфраструктуру обмена активами, доступную каждому устройству без дополнительных затрат на внедрение.

Таким образом, TRS — это философия минимализма: не строить новое, а использовать уже существующее, превращая каждый смартфон в узел доверия.
