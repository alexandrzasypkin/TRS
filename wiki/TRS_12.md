# 12. ГЛОССАРИЙ

[↑ Вернуться к оглавлению](Home.md)


> Данный глоссарий содержит определения всех специализированных терминов TRS, используемых в документации. Термины упорядочены по алфавиту (сначала на латинице, затем на кириллице).

------------------------------------------------------------------------

## A

### Arbitrator — Арбитр

**Определение:** Независимая сторона, назначаемая для разрешения спорных ситуаций между клиентами TRS.

**Описание:** Арбитр может быть назначен заранее (в условиях Transaction Record) или выбран участниками в процессе спора. Решение арбитра оформляется как подписанный документ и может служить основанием для отзыва или перевыпуска сертификатов. Арбитр также является клиентом системы и имеет собственный X.509 сертификат.

**Применение:** Споры по качеству услуг, несоответствие товара описанию, конфликты при Offline Mode.

------------------------------------------------------------------------

### ASN.1 (Abstract Syntax Notation One) — Абстрактная синтаксическая нотация

**Определение:** Стандарт описания структур данных, используемый в X.509 сертификатах и PKI.

**Описание:** ASN.1 определяет, как данные организованы (структура), а DER определяет, как они кодируются (бинарное представление). В TRS ASN.1 используется для описания структуры произвольных расширений (OID) в Asset Certificate.

**Пример структуры Asset Information:**  
```  
DivisibleAsset ::= SEQUENCE {  
assetID UTF8String,  
assetType UTF8String,  
assetSubtype UTF8String,  
unit UTF8String,  
quantity INTEGER,  
totalOriginal INTEGER,  
divisible BOOLEAN,  
gatewayID UTF8String,  
registrationTx UTF8String,  
issuedAt GeneralizedTime,  
parentCertSerial UTF8String OPTIONAL,  
splitFrom UTF8String OPTIONAL  
}  
```

**Применение:** Определение структуры расширений X.509, кодирование в DER для передачи и хранения.

**См. также:** DER, OID, X.509

------------------------------------------------------------------------

### Asset — Актив

**Определение:** Единица ценности (деньги, товар, цифровой предмет, право, услуга), обращающаяся в TRS.

**Описание:** Актив существует в форме Asset Certificate (X.509 сертификата), имеет тип (`assetType`), подтип (`assetSubtype`), объём (`quantity`), владельца (`client_id`) и полную цепочку происхождения (`parentCertSerial`, `splitFrom`). Каждый актив удостоверяется Gateway и подписывается CA.

**Типы активов:**

- CURRENCY — валюты и денежные средства (RUR, USD, EUR, BTC)
- COMMODITY — товары и материалы (песок, металл, зерно)
- DIGITAL — цифровые предметы (игровые скины, NFT, токены)
- SERVICE — услуги и права (консультация, лицензия, подписка)

**См. также:** Asset Certificate, Asset Type, Divisible Asset

------------------------------------------------------------------------

### Asset Certificate — Сертификат актива

**Определение:** Цифровой сертификат X.509, подтверждающий владение активом в TRS.

**Описание:** Основная единица учёта в системе. Содержит идентификатор актива (`assetID`), тип (`assetType`), объём (`quantity`), владельца (Subject CN), источник происхождения (`gatewayID`, `registrationTx`) и связь с родительскими сертификатами (`parentCertSerial`). Сертификат подписывается CA и публикуется в Public Repository. Формат: стандартный X.509 v3 с произвольными расширениями (OID).

**Жизненный цикл:** Выпуск (Registration) → Использование (Transfer/Swap) → Деление (Split, опционально) → Отзыв (Revocation).

**См. также:** X.509, OID, Public Repository, CRL

------------------------------------------------------------------------

### Asset Registration — Регистрация актива

**Определение:** Процесс ввода новой ценности в систему TRS через доверенный Gateway (Cash-in).

**Описание:** Клиент формирует CSR (Certificate Signing Request) с параметрами актива. Gateway подтверждает происхождение ценности, подписывая запрос своей цифровой подписью. CA проверяет данные и выпускает Asset Certificate, фиксирующий факт владения активом. Процесс универсален для всех типов активов: финансовых, товарных, виртуальных или юридических.

**Этапы:**  
1. Внесение/передача актива Gateway  
2. Формирование CSR клиентом  
3. Подпись CSR Gateway (подтверждение происхождения)  
4. Проверка CA (валидация Gateway, данных)  
5. Выпуск Asset Certificate  
6. Публикация в Public Repository

**Примеры:** Пополнение счёта через банк, размещение товара на складе, регистрация услуги на платформе.

**Устаревший термин:** Cash In (не рекомендуется, слишком узкий для универсальной системы).

**См. также:** Gateway, CSR, CA

------------------------------------------------------------------------

### Asset Revocation — Отзыв актива

**Определение:** Процесс аннулирования Asset Certificate, делающий его недействительным для дальнейшего использования.

**Описание:** Применяется при завершении сделки (автоматический отзыв при Atomic Swap или Asset Transfer), утере ключей, компрометации сертификата или по решению Arbitrator. Отозванные сертификаты публикуются в CRL (Certificate Revocation List) и становятся недоступными для операций. Любая попытка использовать отозванный сертификат отклоняется Routing Core при проверке через CRL/OCSP.

**Причины отзыва:**

- Передача актива другому клиенту (Atomic Swap, Asset Transfer)
- Вывод актива из системы (Withdrawal через Gateway)
- Деление актива (Asset Split — исходный отзывается, выпускаются дочерние)
- Компрометация приватного ключа владельца
- Решение арбитра при спорных ситуациях
- Истечение срока действия сертификата

**См. также:** CRL, OCSP, Transaction Record

------------------------------------------------------------------------

### Asset Split — Деление актива

**Определение:** Разделение одного Asset Certificate на несколько дочерних сертификатов с сохранением общего объёма.

**Описание:** Применяется для делимых активов (divisible=true). Все дочерние сертификаты наследуют параметр `totalOriginal` (исходное количество) и цепочку происхождения (`parentCertSerial`). Сумма `quantity` всех дочерних сертификатов должна равняться `quantity` исходного сертификата. Исходный сертификат отзывается CA, новые публикуются в Public Repository.

**Правила деления:**

- Применимо только к делимым активам (CURRENCY, COMMODITY с divisible=true)
- Сумма частей = исходному количеству
- `totalOriginal` сохраняется во всех дочерних сертификатах
- `parentCertSerial` указывает на исходный сертификат
- `splitFrom` содержит ID транзакции деления

**Примеры:**

- 5000 кг песка → 2000 кг + 3000 кг
- 1200 RUR → 500 RUR + 700 RUR
- 100 лицензий Office 365 → 60 + 40

**См. также:** Divisible Asset, totalOriginal, parentCertSerial

------------------------------------------------------------------------

### Asset Transfer — Передача актива

**Определение:** Перемещение права собственности на актив от одного клиента к другому.

**Описание:** Реализуется через механизм Atomic Swap (в случае встречного обмена) или простую передачу (в случае одностороннего движения, например, дарение). Исходные сертификаты отзываются CA, новые выпускаются на имя получателей. Операция атомарна — либо все сертификаты обновляются одновременно, либо операция отменяется полностью.

**Режимы:**

- **Online Mode** — мгновенная обработка через Routing Core (5-20 секунд)
- **Offline Mode** — локальное подписание через QR/NFC, публикация при появлении интернета

**См. также:** Atomic Swap, Transaction Record, Online Mode, Offline Mode

------------------------------------------------------------------------

### Asset Type — Тип актива

**Определение:** Категория актива, определяющая его базовые свойства и правила обращения.

**Описание:** Хранится в поле `assetType` расширения Asset Certificate. Определяет, является ли актив делимым, как проверяется его подлинность, и какие Gateway могут его регистрировать.

**Основные типы:**

- **CURRENCY** — валюты, деньги (всегда делимые)
- **COMMODITY** — товары, сырьё, материалы (могут быть делимыми или неделимыми)
- **DIGITAL** — цифровые предметы (обычно неделимые, кроме токенов)
- **SERVICE** — услуги, права, лицензии (могут быть делимыми для подписок)

**Дополнение:** `assetSubtype` уточняет конкретный вид (RUR, USD, BTC, SAND, скин AWP, консультация юриста).

**См. также:** assetSubtype, unit, Divisible Asset

------------------------------------------------------------------------

### Atomic Swap — Атомарный обмен

**Определение:** Одновременная взаимная передача активов между двумя или более клиентами с гарантией целостности (“всё или ничего”).

**Описание:** Сделка совершается только при наличии подписей всех участников. CA выполняет операции в рамках одной транзакции (ACID): отзыв старых сертификатов и выпуск новых происходят атомарно. Если хотя бы одна операция не может быть выполнена (например, сертификат уже отозван), вся транзакция откатывается (rollback). Механизм исключает частичное исполнение и double-spending.

**Преимущества:**

- Гарантия “всё или ничего” на криптографическом уровне
- Нет необходимости в эскроу или посредниках
- Работает для любых комбинаций активов (товар↔товар, товар↔деньги, услуга↔деньги)
- Поддерживает Offline Mode (встречные CSR с взаимными подписями)

**Применение:** Базовый механизм всех обменов в TRS — от простых P2P переводов до сложных многосторонних сделок.

**См. также:** Transaction Record, CSR, double-spending

------------------------------------------------------------------------

### Audit Log — Журнал аудита

**Определение:** Неизменяемый журнал всех операций с сертификатами и транзакциями в TRS.

**Описание:** Фиксирует выпуск, отзыв, подписи и публикации. Используется для аудита, расследований и регуляторных проверок. Каждая запись содержит timestamp, подписи участников, хеши сертификатов и статусы операций. Журнал хранится в Routing Core и может быть распределён между несколькими узлами в федеративной архитектуре.

**См. также:** Routing Core, Public Repository

------------------------------------------------------------------------

## B

### Bilateral Netting — Двусторонний неттинг

**Определение:** Взаимозачёт обязательств между двумя клиентами с расчётом чистой позиции.

**Описание:** Сводит множество встречных операций за период (день, неделю) в одну финальную. Используется для оптимизации числа транзакций и снижения комиссий. Реализуется через механизм Settlement в Routing Core.

**Пример:** Компания A продала B товаров на 500,000₽, B продала A товаров на 300,000₽ → чистая позиция: A должна получить 200,000₽ (вместо двух операций по 500К и 300К).

**См. также:** Multilateral Netting, Settlement, Routing Core

------------------------------------------------------------------------
### Business Layer — Прикладной уровень TRS

**Определение:** Совокупность отраслевых решений и интеграций (финансы, торговля, госуслуги), использующих единый технологический стек TRS для обмена активами.

**См. также:** Value Routing, Gateway Federation.
------------------------------------------------------------------------

## C

### CA (Certificate Authority) — Центр сертификации

**Определение:** Доверенный узел TRS, выпускающий, проверяющий и отзывающий X.509 сертификаты.

**Описание:** Выполняет роль нотариуса — подтверждает владение активами через цифровые подписи, но не владеет активами и не может распоряжаться ими. CA проверяет CSR от клиентов, подписи Gateway, корректность данных и выпускает Asset Certificate. Публикует CRL (списки отозванных сертификатов) и обслуживает OCSP для проверки статусов. Может работать автономно (stand-alone) или в составе федерации (федеративный режим с кворумом).

**Функции:**

- Выпуск Asset Certificate и Client Certificate
- Проверка CSR и подписей Gateway
- Отзыв сертификатов (Revocation)
- Публикация CRL/OCSP
- Ведение журнала операций

**Принцип:** CA как нотариус, а не владелец — удостоверяет факт владения, но не управляет активами.

**См. также:** CSR, CRL, OCSP, Federation

------------------------------------------------------------------------

### Certificate Lifecycle — Жизненный цикл сертификата

**Определение:** Последовательность стадий существования Asset Certificate — от выпуска до отзыва или истечения срока действия.

**Описание:** Контролируется Routing Core и CA. Включает регистрацию (Registration), использование (Transfer/Swap), опциональное деление (Split) и финальный отзыв (Revocation) или архивирование после истечения срока.

**Стадии:**  
1. **Pending** — CSR сформирован, ожидает подписи CA  
2. **Active** — сертификат выпущен и действителен  
3. **Transferred** — отозван в результате передачи другому клиенту  
4. **Split** — отозван в результате деления на части  
5. **Revoked** — отозван по иным причинам (компрометация, решение арбитра)  
6. **Expired** — истёк срок действия

**См. также:** Asset Certificate, CRL, Public Repository

------------------------------------------------------------------------

### Client — Клиент

**Определение:** Основная учётная единица TRS — физическое лицо, организация, сервис или шлюз.

**Описание:** Любой участник обмена активами в TRS рассматривается как клиент системы. Каждый клиент имеет собственный X.509 Client Certificate, аутентифицируется через контейнер PKCS#12 и участвует в обмене по единым криптографическим правилам. Клиенты равноправны — нет разделения на “важных” и “второстепенных” участников.

**Типы клиентов:**

- **Физические лица** (User) — индивидуальные пользователи
- **Организации** — компании, холдинги, государственные органы
- **Шлюзы** (Gateway) — точки входа/выхода активов
- **Сервисы** — платформы, маркетплейсы, биржи

> **Важно:** В TRS все участники (включая Gateway и банки) являются клиентами. Шлюзы не выступают как внешние посредники, а рассматриваются как равноправные участники системы обмена.

**См. также:** User, Gateway, Client Certificate

------------------------------------------------------------------------

### Client Certificate — Клиентский сертификат

**Определение:** X.509 сертификат, удостоверяющий личность клиента в TRS.

**Описание:** Используется для аутентификации при взаимодействии с Routing Core (X.509 ClientAuth), подписания Transaction Record и CSR. Хранится в PKCS#12 контейнере вместе с приватным ключом. Выпускается CA при регистрации клиента в системе.

**Отличие от Asset Certificate:** Client Certificate удостоверяет личность участника, Asset Certificate — владение активом.

**См. также:** PKCS#12 Wallet, X.509 ClientAuth

------------------------------------------------------------------------

### CRL (Certificate Revocation List) — Список отозванных сертификатов

**Определение:** Публичный список серийных номеров отозванных сертификатов, публикуемый CA.

**Описание:** Обновляется периодически (обычно каждые 24 часа или при значительных изменениях). Клиенты и Routing Core проверяют CRL перед принятием сертификата в транзакции, чтобы убедиться, что сертификат не был отозван. Публикуется в Public Repository по стандартному URI (например, https://repo.trs/crl/latest.crl).

**Формат:** Стандартный X.509 CRL (RFC 5280), содержит серийные номера, даты отзыва и причины.

**Альтернатива:** OCSP (Online Certificate Status Protocol) — для real-time проверки статуса отдельного сертификата.

**См. также:** OCSP, Public Repository, Asset Revocation

------------------------------------------------------------------------

### CSR (Certificate Signing Request) — Запрос на подпись сертификата

**Определение:** Стандартный PKCS#10 запрос, содержащий параметры будущего сертификата и подпись клиента.

**Описание:** Формируется клиентом при регистрации актива или операции обмена. Содержит публичный ключ клиента, Subject (идентификатор), расширения (тип актива, количество, Gateway и т.д.) и подпись приватным ключом клиента. В случае Asset Registration CSR также подписывается Gateway для подтверждения происхождения актива. CA проверяет CSR и, если всё корректно, выпускает Asset Certificate.

**Применение в Atomic Swap:** Каждый участник формирует CSR для запроса нового сертификата. CSR содержат хеши CSR контрагентов для обеспечения взаимности.

**См. также:** PKCS#10, Asset Registration, Atomic Swap

------------------------------------------------------------------------

### CBOR (Concise Binary Object Representation) — Компактное бинарное представление объектов

**Определение:** Бинарный формат сериализации данных (RFC 8949), аналог JSON, но компактнее и быстрее.

**Описание:** В TRS CBOR может использоваться как альтернатива JSON для представления Transaction Record, особенно в IoT-устройствах и встроенных системах. CBOR кодирует те же структуры данных, что и JSON, но в бинарном виде, что снижает размер на 50-70% и ускоряет парсинг.

**Преимущества:**

- Компактность — в 2-3 раза меньше JSON
- Скорость парсинга — бинарный формат быстрее
- Поддержка бинарных данных — без base64-кодирования

**Применение в TRS:**

- Transaction Record для IoT-устройств
- Offline Mode с ограниченной памятью
- NFC-обмен (размер данных критичен)

**Подпись CBOR:**  
COSE (CBOR Object Signing and Encryption, RFC 8152) — стандарт для подписания CBOR-документов, аналог JWS для JSON.

**Сравнение размеров Transaction Record:**

| Формат        | Размер     | Применение               |
|---------------|------------|--------------------------|
| JSON + JWS    | ~2500 байт | REST API, веб-интерфейсы |
| XML + XMLDSig | ~4000 байт | Корпоративные системы    |
| CBOR + COSE   | ~1200 байт | IoT, NFC, embedded       |
| PKCS#10 (CSR) | ~800 байт  | Чистый PKI-подход        |

> CBOR в TRS — опциональный формат. Основа системы — X.509 и CSR (PKCS#10).

**См. также:** JSON, XML, Transaction Record, Offline Mode

------------------------------------------------------------------------

## D

### Digital Asset — Цифровой актив

**Определение:** Актив, существующий исключительно в цифровой форме без физического воплощения.

**Описание:** Подтип активов (`assetType=DIGITAL`) в TRS, включающий игровые предметы, NFT, токены, виртуальную валюту, цифровые права и лицензии. В отличие от физических активов (COMMODITY) или финансовых инструментов (CURRENCY), Digital Asset существует только в виртуальном пространстве. Однако в TRS все цифровые активы получают такой же Asset Certificate, как и физические товары, обеспечивая единообразие обмена.

**Примеры:**

- Игровые скины и оружие (CS:GO AWP Dragon Lore, Fortnite Outfits)
- NFT (цифровое искусство, коллекционные предметы)
- Внутриигровая валюта (золото в WoW, V-Bucks в Fortnite)
- Цифровые права (стриминг-подписки, доступ к контенту)
- Виртуальные токены (не блокчейн-криптовалюты, а платформенные)

**Особенности:**

- Обычно неделимы (divisible=false), кроме виртуальной валюты
- Подтверждаются Gateway (игровая платформа, маркетплейс)
- Могут обмениваться между играми (межигровой обмен)

**См. также:** Asset Type, Service, Gateway

------------------------------------------------------------------------

### Divisible Asset — Делимый актив

**Определение:** Актив, который можно разделить на части без потери свойств и с сохранением общего объёма.

**Описание:** В Asset Certificate имеет флаг `divisible=true`. Используется для валют, материалов, токенов и долевых прав. При делении (Asset Split) исходный сертификат отзывается, выпускаются дочерние сертификаты с сохранением `totalOriginal`.

**Примеры делимых активов:**

- Валюты (RUR, USD, BTC) — всегда делимы
- Сыпучие материалы (песок, цемент, зерно)
- Жидкости (нефть, вода)
- Токены и цифровые валюты
- Плавающие лицензии (можно разделить пул лицензий)

**Неделимые активы:**

- Уникальные предметы (автомобиль, картина)
- Персональные услуги (консультация конкретного специалиста)
- NFT и уникальные цифровые предметы

**См. также:** Asset Split, totalOriginal

------------------------------------------------------------------------

### Double-Spending Prevention — Предотвращение двойного расходования

**Определение:** Механизм TRS, гарантирующий однократное использование каждого Asset Certificate.

**Описание:** При передаче или обмене актива исходный сертификат немедленно отзывается CA и публикуется в CRL. Routing Core проверяет CRL перед принятием любой транзакции. Попытка использовать отозванный сертификат отклоняется. В Offline Mode защита обеспечивается через Grace Period — транзакция может быть оспорена в течение заданного времени.

**Механизмы защиты:**

- Атомарность операций CA (ACID транзакции)
- Немедленная публикация CRL после отзыва
- Проверка статуса через CRL/OCSP перед каждой операцией
- Grace Period для Offline Mode
- Публичность репозитория (любой может проверить статус)

**См. также:** CRL, OCSP, Atomic Swap, Grace Period

------------------------------------------------------------------------

## E

### Escrow — Эскроу

**Определение:** Механизм временного удержания активов третьей стороной до выполнения условий сделки.

**Описание:** В традиционных системах эскроу-агент блокирует деньги или товары до подтверждения. В TRS эскроу не требуется для большинства операций благодаря Atomic Swap, который гарантирует одновременный обмен без посредника. Однако для некоторых сценариев (например, услуги с отложенным подтверждением) TRS поддерживает эскроу через блокировку сертификата с условием разблокировки по подписям участников или Arbitrator.

**Сравнение:**

- Традиционный эскроу: комиссия 2-5%, время 1-7 дней, зависимость от агента
- TRS Atomic Swap: комиссия 0.1-0.5%, время 5-20 секунд, нет посредника

**См. также:** Atomic Swap, Arbitrator

------------------------------------------------------------------------

## F

### Federation — Федерация

**Определение:** Распределённая модель доверия, где несколько CA подтверждают операции совместно.

**Описание:** Повышает надёжность и исключает монополию одного центра. Используется в случаях, когда требуется высокая устойчивость (государственные реестры, крупные биржи) или когда участники не доверяют одному CA. Решения принимаются по принципу кворума (например, 3 из 5 CA должны подписать транзакцию).

**Модели:**

- **Stand-alone** — один CA (проще, быстрее)
- **Federated** — несколько CA с кворумом (надёжнее, медленнее)

**См. также:** CA, Federation Quorum

------------------------------------------------------------------------

### Federation Quorum — Кворум федерации

**Определение:** Минимальное количество подписей CA, необходимое для подтверждения операции в федеративном режиме.

**Описание:** Используется в федеративной модели доверия. Например, при кворуме “3 из 5” транзакция считается подтверждённой, если её подписали минимум 3 CA из 5 участников федерации. Защищает от компрометации одного или двух CA.

**Применение:** Критичные системы (государственные реестры, крупные биржи), где требуется максимальная защита от манипуляций.

**См. также:** Federation, CA

------------------------------------------------------------------------

## G

### Gateway — Шлюз

**Определение:** Доверенная точка входа/выхода активов в TRS, являющаяся равноправным клиентом системы.

**Описание:** Подтверждает происхождение ценностей своей цифровой подписью при Asset Registration и обеспечивает конвертацию между TRS и внешними системами (банки, склады, платформы). Gateway не выступает как посредник, а является участником обмена со своим Client Certificate.

**Функции:**

- Подтверждение происхождения активов (подпись CSR)
- Выдача активов при предъявлении сертификата (склад отдаёт товар)
- Конвертация в/из внешних систем (банк → TRS, TRS → банк)
- Проверка качества и подлинности активов

**Типы Gateway:**

- **Финансовые** — банки, платёжные системы, обменники
- **Товарные** — склады ответственного хранения, логистические центры
- **Цифровые** — игровые платформы, маркетплейсы, фриланс-биржи
- **Сервисные** — регистраторы лицензий, нотариусы, регуляторы

**Экономика:** Gateway получает комиссию за услуги подтверждения (обычно 0.05-0.2% от суммы актива).

**См. также:** Asset Registration, Withdrawal, Client

------------------------------------------------------------------------
### Gateway Commission — Комиссия шлюза

**Определение:** Вознаграждение, которое получает Gateway за подтверждение происхождения актива или операцию вывода/ввода.

**Описание:** Размер комиссии определяется политикой шлюза и фиксируется в Transaction Record.

------------------------------------------------------------------------
### Grace Period — Период отсрочки

**Определение:** Интервал времени, в течение которого Offline-транзакция может быть оспорена после публикации.

**Описание:** Применяется для защиты от мошенничества в Offline Mode. Например, если Grace Period = 24 часа, то после публикации офлайн-сделки любой участник может её оспорить в течение суток. Если оспаривания нет, транзакция становится окончательной. Если оспаривание подано, привлекается Arbitrator для разбирательства.

**Типичные значения:**

- Мелкие сделки (< 10,000₽): 1-4 часа
- Средние сделки (10K-100K₽): 12-24 часа
- Крупные сделки (> 100K₽): 48-72 часа

**См. также:** Offline Mode, Arbitrator, double-spending

------------------------------------------------------------------------

## I

### Issuer — Издатель (эмитент)

**Определение:** Сторона, выпустившая и подписавшая X.509 сертификат (обычно CA).

**Описание:** Поле Issuer в X.509 сертификате содержит Distinguished Name (DN) Certificate Authority, которая выпустила данный сертификат. Позволяет построить Trust Chain — цепочку доверия от сертификата до корневого CA. Клиенты проверяют Issuer, чтобы убедиться, что сертификат выпущен доверенным CA.

**Формат:** `Issuer: CN=TRS CA, O=Treasures Routing System, C=NL`

**Применение:** Проверка подлинности Asset Certificate и Client Certificate, построение цепочки доверия.

**См. также:** CA, Subject, Trust Chain, X.509

------------------------------------------------------------------------

## J

### JSON / JWS — JSON и JSON Web Signature

**Определение:** Формат сериализации данных (JSON) и стандарт цифровой подписи для JSON-документов (JWS, RFC 7515).

**Описание:** В TRS JSON используется как **опциональный формат** для представления Transaction Record (наравне с PKCS#7, XML, CBOR). JWS обеспечивает подписание JSON-документов цифровыми подписями. Хотя JSON удобен для REST API и веб-интерфейсов, TRS **не привязана к JSON** — основой остаются X.509 сертификаты и CSR (PKCS#10).

**Применение:**

- Transaction Record в REST API (удобство для веб/мобильных клиентов)
- Readable формат для отладки
- Интеграция с JavaScript-приложениями

**Альтернативы:**

- PKCS#7/CMS — чистый PKI-подход (основной)
- XML+XMLDSig — для корпоративных систем
- CBOR+COSE — для IoT и embedded

> **Важно:** JSON в TRS — это удобная надстройка для API, а не обязательное требование. Система работает на базе X.509 и CSR.

**См. также:** Transaction Record, PKCS#10, XML, CBOR

------------------------------------------------------------------------

## K

### Key Usage — Использование ключа

**Определение:** Стандартное расширение X.509 сертификата, определяющее допустимые операции с публичным ключом.

**Описание:** Указывает, для каких целей может использоваться ключ из сертификата. Помечается как critical (критичное) — приложения должны отклонить сертификат, если не понимают значения. В TRS используется для разграничения Client Certificate (подпись транзакций) и CA Certificate (подпись других сертификатов).

**Типичные значения:**

- `digitalSignature` — подпись документов и транзакций (Client Certificate, Asset Certificate)
- `keyEncipherment` — шифрование ключей (для дополнительной безопасности)
- `keyCertSign` — подпись других сертификатов (только CA)
- `cRLSign` — подпись списков отозванных сертификатов (только CA)

**Пример для Client Certificate:**  
```  
X509v3 Key Usage: critical  
Digital Signature, Key Encipherment  
```

**Пример для CA Certificate:**  
```  
X509v3 Key Usage: critical  
Digital Signature, Certificate Sign, CRL Sign  
```

**См. также:** X.509, Client Certificate, CA, Extended Key Usage

------------------------------------------------------------------------

## L

### Ledger — Реестр (распределённый журнал)

**Определение:** Термин из блокчейн-технологий, обозначающий общий неизменяемый журнал всех транзакций.

**Описание:** В блокчейне Ledger — это глобальный реестр, реплицируемый на всех нодах. TRS **не использует глобальный Ledger** — вместо этого система опирается на:

- **Asset Certificate** — локальные сертификаты владения
- **Public Repository** — публичное хранилище сертификатов (не реплицируемый реестр, а простой HTTP-репозиторий)
- **Audit Log** — журнал операций в Routing Core (локальный, не глобальный)

**Сравнение:**

| Характеристика    | Blockchain Ledger          | TRS                                  |
|-------------------|----------------------------|--------------------------------------|
| Глобальный реестр | Да (все ноды хранят копию) | Нет (локальные сертификаты)          |
| Неизменяемость    | Да (блоки связаны хешами)  | Частичная (сертификаты подписаны CA) |
| Репликация        | Полная (на всех нодах)     | Минимальная (Public Repository)      |
| Консенсус         | Требуется (PoW, PoS, etc.) | Не требуется (доверие к CA)          |

> TRS демонстрирует, что прозрачность и проверяемость возможны без глобального Ledger — достаточно публичного репозитория сертификатов и стандартных PKI-механизмов.

**См. также:** Public Repository, Audit Log, Asset Certificate

------------------------------------------------------------------------

## M

### Multilateral Netting — Многосторонний неттинг

**Определение:** Взаимозачёт обязательств между тремя и более клиентами с расчётом чистых позиций каждого.

**Описание:** Оптимизирует расчёты при большом числе участников и встречных обязательств. Routing Core анализирует все транзакции за период, вычисляет чистые позиции и выпускает финальные сертификаты через Settlement. Снижает число реальных операций в разы.

**Пример:** 10 компаний совершили 50 взаимных сделок за день → после неттинга остаётся 10 финальных позиций (по одной на компанию).

**См. также:** Bilateral Netting, Settlement, Routing Core

------------------------------------------------------------------------

## N

### Netting — Неттинг

**Определение:** Общий механизм взаимозачёта встречных обязательств между клиентами.

**Описание:** Включает двусторонний (Bilateral) и многосторонний (Multilateral) неттинг. Используется для оптимизации числа операций, снижения комиссий и упрощения учёта. Особенно эффективен на биржах и в корпоративных системах с большим числом встречных потоков.

**См. также:** Bilateral Netting, Multilateral Netting, Settlement

------------------------------------------------------------------------

### Novation — Новация

**Определение:** Замена цепочки промежуточных обязательств одним итоговым сертификатом.

**Описание:** Сокращает объём хранимых данных и упрощает аудит. Например, если актив прошёл через 10 владельцев, можно заменить цепочку из 10 сертификатов одним финальным (с сохранением `totalOriginal` и начального `assetID`).

**Применение:** Архивирование долгих цепочек, оптимизация хранения в Public Repository.

**См. также:** Asset Certificate, parentCertSerial

------------------------------------------------------------------------

## O

### Offline Mode — Офлайн-режим

**Определение:** Режим выполнения транзакций без подключения к интернету с отложенной публикацией.

**Описание:** Участники подписывают Transaction Record локально (через QR-коды или NFC), обмениваются CSR и сертификатами на месте. Транзакция считается локально подтверждённой, но окончательной становится только после публикации в Routing Core при появлении интернета. Защищён через Grace Period — возможность оспорить транзакцию в течение определённого времени.

**Применение:** Встречи в удалённых местах, сделки в метро/самолёте, страны с плохим интернетом.

**См. также:** Online Mode, Grace Period, QR, NFC

------------------------------------------------------------------------

### Online Mode — Онлайн-режим

**Определение:** Режим мгновенной обработки транзакций с проверкой CA и публикацией в реальном времени.

**Описание:** Стандартный режим работы TRS. Routing Core проверяет подписи, статусы сертификатов (CRL/OCSP), выполняет Atomic Swap и публикует результат в Public Repository. Среднее время обработки: 5-20 секунд от подписания Transaction Record до получения новых сертификатов.

**См. также:** Offline Mode, Routing Core

------------------------------------------------------------------------

### OCSP (Online Certificate Status Protocol) — Протокол проверки статуса сертификата

**Определение:** Протокол для real-time проверки, не отозван ли конкретный сертификат.

**Описание:** Альтернатива CRL для случаев, когда нужна мгновенная проверка одного сертификата (вместо загрузки всего списка отозванных). Клиент отправляет запрос OCSP с серийным номером сертификата, CA отвечает статусом: Good (действителен), Revoked (отозван), Unknown (неизвестен).

**Преимущества перед CRL:**

- Мгновенная проверка (не нужно загружать весь список)
- Меньше трафика
- Актуальность (статус проверяется в реальном времени)

**См. также:** CRL, Asset Revocation

------------------------------------------------------------------------

## P

### PKCS#12 Wallet — Кошелёк PKCS#12

**Определение:** Контейнер, хранящий приватный ключ и Client Certificate клиента в зашифрованном виде.

**Описание:** Используется для идентификации клиента и подписи транзакций. Поддерживается системными средствами всех современных устройств: iOS Keychain, Android Keystore, Windows CertStore, macOS Keychain. Защищён паролем или биометрией. Содержит также цепочку CA-сертификатов для проверки подписей.

**Хранение:**

- Локально на устройстве (смартфон, компьютер)
- Опционально: резервная копия в облаке (зашифрована)
- Аппаратные токены (Yubikey, смарт-карты) для повышенной безопасности

**См. также:** Client Certificate, X.509 ClientAuth

------------------------------------------------------------------------

### Proof of Origin — Доказательство происхождения

**Определение:** Цифровое подтверждение происхождения актива, сформированное Gateway и встроенное в расширения X.509 сертификата.
Поля: `gateway`, `gatewaySignature`, `registrationTimestamp`.

------------------------------------------------------------------------

### Public Repository — Публичный репозиторий

**Определение:** Открытое хранилище Asset Certificate, CRL и OCSP, доступное всем участникам для проверки.

**Описание:** Публикует активные и отозванные сертификаты, обеспечивает прозрачность и проверку статусов. Любой клиент (или внешний наблюдатель) может проверить подлинность сертификата, его владельца, историю передач и текущий статус. Реализуется как простое HTTP-хранилище с `.crt` и `.crl` файлами, доступными по URI.

**Структура:**

- `/certs/` — активные сертификаты (по серийным номерам)
- `/crl/` — списки отозванных сертификатов
- `/clients/` — публичные Client Certificate участников (опционально)

**Прозрачность:** Основа доверия в TRS — все операции публичны и проверяемы.

**См. также:** CRL, OCSP, Asset Certificate

------------------------------------------------------------------------

## R

### Routing Core — Центр маршрутизации активов

**Определение:** Центральный компонент TRS, обрабатывающий транзакции, выполняющий верификацию подписей, управление журналом аудита и публикацию в Public Repository.
**Описание:** Фиксирует все транзакции, взаимодействует с CA для выпуска/отзыва сертификатов, публикует результаты в Public Repository. Проверяет подписи участников, статусы сертификатов (CRL/OCSP), выполняет Atomic Swap и Settlement (неттинг). Ведёт Audit Log всех операций.

**Функции:**

- Приём Transaction Record от клиентов
- Проверка подписей и статусов сертификатов
- Координация с CA для выпуска/отзыва
- Публикация результатов в Public Repository
- Выполнение Settlement (клиринг, неттинг)
- Ведение журнала аудита
- Atomic Swap, Asset Transfer, CRL/OCSP обновления, Federated CA синхронизация.

**Архитектура:** Может работать как централизованный сервис (stand-alone) или распределённая сеть (Routing Federation).

**См. также:** CA, Transaction Record, Settlement

------------------------------------------------------------------------

### Routing Core API — API Центра маршрутизации

**Определение:** Интерфейс взаимодействия клиентов с Routing Core через HTTPS.

**Описание:** Реализует операции через REST API, GraphQL или WebSocket с обязательной клиентской аутентификацией X.509 ClientAuth. Основные эндпоинты: `/register_asset`, `/transfer_asset`, `/get_asset_status`, `/list_certificates`.

**Подробнее см. раздел 9.6 API-интерфейсы.**

**См. также:** Routing Core, X.509 ClientAuth

------------------------------------------------------------------------

### Routing Federation — Федерация маршрутизации

**Определение:** Сеть доверенных узлов Routing Core, объединённых общими правилами подписания.

**Описание:** Поддерживает мультиподписи и совместную валидацию. Используется для повышения надёжности и децентрализации в крупных системах (государственные реестры, международные биржи).

**См. также:** Routing Core, Federation, Federation Quorum

------------------------------------------------------------------------

### Routing Transaction — Маршрутная транзакция

**Определение:** Совокупность связанных операций по обмену активами (Atomic Swap, Transfer, Split).

**Описание:** Включает отзыв старых сертификатов и выпуск новых, фиксируется в Audit Log Routing Core. Каждая Routing Transaction имеет уникальный `transaction_id` и содержит подписи всех участников.

**См. также:** Transaction Record, Atomic Swap, Asset Transfer

------------------------------------------------------------------------

## S

### Service — Услуга (тип актива)

**Определение:** Тип актива (`assetType=SERVICE`) в TRS, представляющий право на получение услуги или временный доступ к ресурсу.

**Описание:** В отличие от материальных товаров (COMMODITY) или денег (CURRENCY), Service — это обязательство одной стороны оказать услугу другой. Имеет ограниченный срок действия и может быть как делимым (подписки, часы консультаций), так и неделимым (персональная консультация конкретного специалиста).

**Примеры:**

- Профессиональные услуги (юридическая консультация 1 час, бухгалтерское сопровождение)
- Подписки (доступ к платформе на месяц, стриминг-сервис)
- Лицензии ПО (право использования на год)
- Образовательные услуги (курс, вебинар, тренинг)
- Билеты и бронирования (отель, авиаперелёт, мероприятие)

**Особенности:**

- Часто имеет срок действия (expires_at в сертификате)
- Может быть делимой (10 часов консультаций → 5 + 5)
- После использования отзывается (статус “использована”)
- Подтверждается Gateway (платформа, лицензиар, провайдер услуг)

**Жизненный цикл Service:**  
1. Регистрация (Gateway подтверждает возможность оказать услугу)  
2. Atomic Swap (обмен на деньги или другие активы)  
3. Использование (клиент получает услугу)  
4. Подтверждение (обе стороны подписывают завершение)  
5. Отзыв сертификата (услуга использована)

**См. также:** Asset Type, Digital Asset, Gateway, Asset Revocation

------------------------------------------------------------------------

### Settlement — Расчёт (клиринг)

**Определение:** Итоговый этап клирингового цикла, при котором выпускаются финальные сертификаты, отражающие чистые позиции участников после неттинга.

**Описание:** Routing Core анализирует все транзакции за период (день, неделю), вычисляет чистые позиции клиентов (кто кому должен по итогу) и выпускает финальные Asset Certificate. Все промежуточные сертификаты отзываются. Может выполняться ежедневно, еженедельно или по требованию в зависимости от типа активов и условий платформы.

**Этапы:**  
1. Накопление транзакций за период  
2. Расчёт чистых позиций (Bilateral/Multilateral Netting)  
3. Формирование финальных CSR для каждого клиента  
4. Выпуск новых сертификатов через CA  
5. Отзыв всех промежуточных сертификатов  
6. Публикация результатов в Public Repository

**Применение:** Товарные биржи, корпоративный клиринг, платёжные системы с высокой частотой операций.

**См. также:** Netting, Routing Core, Bilateral Netting, Multilateral Netting

------------------------------------------------------------------------

### Smartphone Node — Смартфон как узел

**Определение:** стройство с мобильным приложением TRS, способное работать автономно, выполнять подписи, обмениваться активами и публиковать транзакции при восстановлении связи.

**Описание:** Благодаря встроенным PKI-средствам (Android Keystore, iOS Keychain) современный смартфон может выпускать, подписывать и проверять сертификаты без специализированного оборудования. Это демонстрирует принцип простоты TRS — не требуются серверы или блокчейн-ноды.

**Функции смартфона в TRS:**

- CA — выпуск Asset Certificate через встроенный Keystore
- Routing Core — обработка Transaction Record
- Public Repository — публикация сертификатов через встроенный HTTP-сервер
- PKCS#12 Wallet — хранение собственных ключей

**См. также:** Stand-alone Mode, PKCS#12 Wallet

------------------------------------------------------------------------

### Stand-alone Mode — Автономный режим

**Определение:** Конфигурация TRS с одним CA, работающая на любом устройстве без внешних зависимостей.

**Описание:** Минимальная конфигурация: CA + Routing Core + PKCS#12 Wallet + веб-сервер. Не требует федерации, внешних баз данных или специализированного оборудования. Может быть развёрнута даже на смартфоне.

**Применение:** Корпоративные системы, локальные платформы, пилотные проекты.

**См. также:** Federation, Smartphone Node

------------------------------------------------------------------------

### Subject — Субъект (владелец сертификата)

**Определение:** Поле X.509 сертификата, содержащее Distinguished Name (DN) владельца сертификата.

**Описание:** Идентифицирует клиента, которому принадлежит сертификат. В TRS поле Subject содержит `client_id` владельца актива (для Asset Certificate) или идентификатор клиента (для Client Certificate). Формат: CN (Common Name), O (Organization), C (Country).

**Примеры:**

- Asset Certificate: `Subject: CN=alice@example.com, O=TRS Client`
- Client Certificate: `Subject: CN=alice@example.com, O=TRS Client`
- Gateway Certificate: `Subject: CN=freepay.gateway, O=Payment Gateway`
- CA Certificate: `Subject: CN=TRS CA, O=Treasures Routing System, C=NL`

**Применение:** Идентификация владельца актива, проверка принадлежности сертификата при подписании транзакций.

**См. также:** Issuer, X.509, Client Certificate, Asset Certificate

------------------------------------------------------------------------

## T

### Timestamp — Временная метка

**Определение:** Момент времени, когда было создано событие (транзакция, сертификат, запись в журнале).

**Описание:** В TRS Timestamp присутствует во всех ключевых структурах:

- **Asset Certificate** — `issuedAt` (время выпуска), `expiresAt` (время истечения)
- **Transaction Record** — `timestamp` (время формирования документа)
- **Audit Log** — каждая запись имеет точное время операции
- **CRL** — время публикации списка отозванных сертификатов

Формат: ISO 8601 (например, `2025-10-13T14:30:00Z`). Обеспечивает хронологический порядок событий, защиту от replay-атак (повторного использования старых транзакций) и возможность аудита.

**Применение:**

- Определение порядка транзакций
- Проверка срока действия сертификатов
- Аудит и расследование инцидентов
- Защита от replay-атак (транзакция с устаревшим timestamp отклоняется)

**Синхронизация времени:** Routing Core и CA должны использовать синхронизированное время (NTP) для корректной работы системы.

**См. также:** Audit Log, Transaction Record, Asset Certificate

------------------------------------------------------------------------

### Transaction Record — Запись транзакции

**Определение:** Подписанный всеми участниками документ, описывающий условия сделки (Atomic Swap, Transfer, Split).

**Описание:** Содержит идентификаторы участников, типы и количества активов, CSR для новых сертификатов, условия обмена и цифровые подписи. Формат не привязан к JSON — может быть PKCS#7/CMS (чистый PKI), JSON+JWS, XML+XMLDSig или CBOR+COSE. Routing Core принимает любой формат с валидными подписями.

**Обязательные поля:**

- `transaction_id` — уникальный идентификатор
- `timestamp` — время формирования
- `type` — тип операции (ASSET_TRANSFER, ATOMIC_SWAP, SPLIT, REGISTRATION)
- `participants` — данные участников (client_id, signatures, CSR)
- `mode` — ONLINE или OFFLINE

**См. также:** Atomic Swap, Asset Transfer, CSR

------------------------------------------------------------------------

### Trust Chain — Цепочка доверия

**Определение:** Последовательность сертификатов от клиента до корневого CA, позволяющая проверить подлинность подписи.

**Описание:** Каждый Asset Certificate содержит Authority Key Identifier, указывающий на CA, который его подписал. CA сам имеет сертификат, подписанный вышестоящим CA (или самоподписанный, если это корневой CA). Клиент может построить цепочку и проверить, что сертификат выпущен доверенным CA.

**Применение:** Проверка подлинности сертификатов, защита от подделок.

**См. также:** CA, X.509, Public Repository

------------------------------------------------------------------------

## U

### Universal PKI Environment — Универсальная PKI-среда

**Определение:** Концепция проектирования TRS, обеспечивающая работу системы без дополнительного специализированного ПО.

**Описание:** Система использует только встроенные PKI-механизмы операционных систем и браузеров. Не требует блокчейн-нод, проприетарных SDK, специализированных серверов или баз данных. Любое устройство с поддержкой PKCS#12 и X.509 может участвовать в TRS.

**Принцип:** Простота развёртывания — работает на 99% устройств “из коробки”.

**См. также:** Stand-alone Mode, Smartphone Node

------------------------------------------------------------------------

### User — Пользователь

**Определение:** Физическое лицо, использующее PKCS#12 Wallet для транзакций в TRS.

**Описание:** Частный случай клиента (Client). Совершает операции онлайн или офлайн, взаимодействуя с TRS через мобильное приложение, веб-интерфейс или Telegram-бота. Имеет собственный Client Certificate и PKCS#12 контейнер с приватным ключом.

> **Важное различие:** **User** — только физические лица. **Client** — любой участник (физлица, организации, шлюзы). В документации TRS предпочтительно использовать термин **Client** как универсальный.

**См. также:** Client, PKCS#12 Wallet, Client Certificate

------------------------------------------------------------------------

## V

### Validator — Валидатор

**Определение:** Независимый узел, проверяющий подписи и целостность транзакций в TRS.

**Описание:** Может входить в кворум CA в федеративном режиме и подтверждать корректность обмена. Не имеет права выпускать сертификаты самостоятельно, но может вето операцию при обнаружении несоответствий.

**Применение:** Федеративные системы с высокими требованиями к безопасности.

**См. также:** Federation, Federation Quorum

------------------------------------------------------------------------

### Value Routing — Маршрутизация ценностей

**Определение:** азовая концепция TRS, в которой ценности (активы) передаются не через единый глобальный реестр, а через маршруты доверия между клиентами, подтверждённые X.509 сертификатами.

**Описание:** Основной принцип TRS — движение активов фиксируется цепочкой X.509 сертификатов с цифровыми подписями. Вместо глобального блокчейна используются локальные сертификаты и публичный репозиторий для проверки. Ценности “маршрутизируются” от клиента к клиенту через Atomic Swap и Transaction Record.

**Философия:** TRS — это не платёжная система и не блокчейн, а **универсальная инфраструктура маршрутизации ценностей**.

**См. также:** Atomic Swap, Asset Certificate, Routing Core

------------------------------------------------------------------------

## W

### Wallet Synchronization — Синхронизация кошелька

**Определение:** Обновление локальных Asset Certificate клиента с Public Repository.

**Описание:** Используется после офлайн-сделок, смены устройства или длительного отсутствия в сети. Клиент загружает актуальные сертификаты, проверяет CRL и обновляет локальное хранилище.

**См. также:** PKCS#12 Wallet, Public Repository, Offline Mode

------------------------------------------------------------------------

### Withdrawal — Вывод актива

**Определение:** Конвертация или удаление актива из TRS через Gateway (Cash-out).

**Описание:** Обратный процесс Asset Registration. Клиент передаёт Asset Certificate Gateway, который конвертирует актив во внешнюю систему (банк выплачивает деньги, склад выдаёт товар). После конвертации сертификат отзывается CA.

**Процесс:**  
1. Клиент предъявляет Asset Certificate Gateway  
2. Gateway проверяет сертификат (CRL/OCSP)  
3. Gateway выдаёт актив во внешней системе  
4. Gateway инициирует отзыв сертификата через CA  
5. CA отзывает сертификат, публикует в CRL

**Примеры:** Вывод денег на банковскую карту, получение товара со склада, активация лицензии ПО.

**Устаревший термин:** Cash Out (не рекомендуется, слишком узкий).

**См. также:** Asset Registration, Gateway, Asset Revocation

------------------------------------------------------------------------

### Extended Key Usage — Расширенное использование ключа

**Определение:** Стандартное расширение X.509, дополняющее Key Usage и указывающее на специфические назначения сертификата.

**Описание:** Уточняет применение сертификата в конкретных протоколах и сценариях. В TRS используется для разграничения Client Certificate (аутентификация в HTTPS) и Asset Certificate (подпись транзакций).

**Типичные значения:**

- `TLS Web Client Authentication` (id-kp-clientAuth) — для Client Certificate
- `Code Signing` (id-kp-codeSigning) — для подписи Transaction Record
- `Email Protection` (id-kp-emailProtection) — для защиты email (опционально)

**Пример для Client Certificate:**  
```  
X509v3 Extended Key Usage:  
TLS Web Client Authentication, Code Signing  
```

**См. также:** Key Usage, X.509, Client Certificate

------------------------------------------------------------------------

## X

### X.509

**Определение:** Международный стандарт цифровых сертификатов открытых ключей (RFC 5280).

**Описание:** В TRS X.509 используется не только как компонент TLS/HTTPS, но и как **базовая единица учёта собственности и обмена активами**. Стандарт обеспечивает универсальность — сертификаты X.509 поддерживаются всеми операционными системами, браузерами и PKI-инфраструктурами.

**Типы X.509 сертификатов в TRS:**

**1. Asset Certificate** — сертификат актива

- Удостоверяет владение активом (товар, деньги, услуга)
- Содержит произвольные расширения (OID) с параметрами актива
- Подписывается CA при Asset Registration
- Отзывается при передаче, делении или выводе актива

**2. Client Certificate** — клиентский сертификат

- Удостоверяет личность клиента в системе
- Используется для аутентификации (X.509 ClientAuth)
- Используется для подписи Transaction Record и CSR
- Хранится в PKCS#12 Wallet

**3. CA Certificate** — сертификат центра сертификации

- Корневой сертификат CA
- Используется для проверки подписей Asset Certificate и Client Certificate
- Публикуется в Public Repository

**Структура X.509 v3:**

- **Subject** — владелец (client_id)
- **Issuer** — CA, выпустивший сертификат
- **Public Key** — публичный ключ владельца
- **Validity** — срок действия (Not Before, Not After)
- **Extensions** — расширения (стандартные и произвольные OID)
- **Signature** — цифровая подпись CA

**Форматы представления:**

- **PEM** — текстовый (base64), удобен для передачи по HTTP
- **DER** — бинарный, компактный (для NFC, QR, Offline Mode)

> X.509 в TRS — это мост между традиционными PKI-системами и новыми моделями обмена активами. Используя стандарт X.509, TRS обеспечивает совместимость с существующей инфраструктурой без необходимости в блокчейне.

**См. также:** Asset Certificate, Client Certificate, CA, OID, PKCS#12, PEM, DER

------------------------------------------------------------------------

### X.509 ClientAuth — Клиентская аутентификация X.509

**Определение:** Механизм взаимной аутентификации в HTTPS, где клиент предъявляет свой X.509 сертификат серверу.

**Описание:** Используется для аутентификации клиентов при взаимодействии с Routing Core API. Клиент предоставляет Client Certificate из PKCS#12 контейнера, сервер проверяет подпись CA и разрешает доступ. Обеспечивает защиту API без паролей или токенов.

**Преимущества:**

- Криптографическая аутентификация (невозможно украсть “пароль”)
- Не требует дополнительных токенов
- Работает на уровне TLS (встроено в HTTPS)

**См. также:** Client Certificate, PKCS#12 Wallet, Routing Core API
